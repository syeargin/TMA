01

Design principles

The hub runs on a schemaless JSON document store with path-based collections, realtime listeners, last-writer-wins writes and no transactions. Access rules are keyed on the viewer's sharing level plus one special rule, {self}, that limits a path to the viewer's own document. Every decision below works within those constraints.

Tenant by path

Each team's data lives under teams/{teamId}/…. Switching teams swaps one set of listeners; nothing team-specific sits at the root.

One writer per document

Family answers live in each person's own mine/{uid} document, so two parents can never overwrite each other. Shared documents are written only by staff.

Identity is owner-only

The account registry (accounts/{uid}) can only be written by the site owner. Every permission the app grants is derived from it.

Validate on read

The client merges family documents and ignores any entry whose writer isn't approved for that family or role. A forged entry is stored but never counts.

Derive, don't store, totals

Fund balance, dues paid and RSVP counts are computed from source rows at read time. No counters to drift under concurrent writes.

Idempotent keys

Confirming a payment writes a ledger document whose id is derived from the source payment, so a double click or retry lands on the same document.

Store ids, never names

Accounts are referenced by opaque user id and people by roster reference. Display names are resolved at render and never frozen into data.

Rules over rows

Weekly practices are stored as recurrence rules and expanded client-side, instead of hundreds of single-practice documents.

Why team data isn't locked per team

Rules accept only literal paths plus the trailing {self} placeholder, so a rule cannot say "members of team X write teams/X/…". Parents also need Editor access to write their own record. Recommendation R1 covers the options.

Writes & consistency

The store is last-writer-wins with no transactions. The design avoids contended documents rather than coordinating them.

mine/{uid} grows by about 12 KB per team per season (RSVPs dominate: ~130 dated entries × ~70 bytes per player). The 256 KB cap allows roughly 20 team-seasons per person. Listeners stay at 12 per view regardless of team count.

09

Recommendations

R1

Enforce team isolation in the database

Option A: publish one rule set per team (teams/X write for staff, teams/X/mine/{self} for families) and republish on team creation. It fits under the 64-rule limit for about 20 teams. Option B: one hub per team, with a lightweight club directory linking them. B isolates completely and removes the capacity ceiling.

R2

Stop every viewer loading every family document

Today each client subscribes to all of mine across all teams. Moving family records to teams/{t}/mine/{self} (needs R1-A rules) limits reads to the open team and cuts download size as the club grows.

R3

Add a season dimension

Key teams by season (a5-13tom-2026) and add an archive action. Archived teams stay readable, drop out of pickers, and their mine entries can be pruned.

R4

Store money as integer cents

Change amount to amountCents to avoid floating-point drift in fund totals. Migrate with a one-pass rewrite of ledger rows and pending payments.

R5

Separate contact details from the roster

Parent phones and emails are readable by anyone the page is shared with. Moving them to a contacts document per player gives one place to tighten later.

R6

Add an audit trail

Append staff edits and approvals to teams/{t}/audit/{yyyy-mm}, one document per month holding an array of events, to stay inside the document cap.

R7

Retire legacy role lists

settings.coordinators / food / finance / admins are now only suggestions when approving accounts. Drop them once every role holder has a linked account.

R8

Scheduled export

No automatic backup exists. A weekly scheduled task can read each team and save JSON snapshots to the project's files.
