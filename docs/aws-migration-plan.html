Team Hub AWS Migration

How the club hub moved from claude.ai to your own AWS account, and what's left before families use it: an AWS SAM stack, invite-only Cognito sign-in, a role-checking API over one DynamoDB table, live updates over WebSockets, and an Angular site, all deployed from GitHub. It now serves many clubs, each with its own colors, and it folds in the October risk assessment and the hardening plan.

03

Architecture

Updated

The browser uses four AWS front doors: CloudFront for the site, Cognito to sign in, the HTTP API to read and write, and the WebSocket API to hear about changes. Only the API function writes team data, so every role rule is enforced on the server. Red tags mark where the open risks sit.

04

Access model

New

Three tiers. Rights only flow down: a site owner is a club admin everywhere, and a club admin is a team admin on every team in their club. Team roles are stored on the membership, never in Cognito, so a role change takes effect on the next API call.

What each team role can do

From api/src/shared/permissions.ts, which the API and the site both import. On an archived team, only the two viewing rights remain.

05

Data model

Updated

One table, TeamHub-<env>. Everything about a team lives in its own partition, so one query loads the team and one partition delete removes it. Club, invite, people and connection records sit in their own partitions.

06

SAM stack

Updated

Two stacks. The one-time bootstrap stack (bootstrap/github-oidc.yaml) creates the GitHub OIDC trust, one deploy role per environment, and the CloudFormation execution role. The app stack (template.yaml) holds everything else, deployed as tma-dev and tma-prod. All functions run Node.js 24 on arm64 with X-Ray tracing and 30-day logs.

Sign-in

Updated

Email and password, invite-only. Admins invite people with their roles and player already attached, so a parent is ready the moment they verify their email. People who already have an account get the new team the next time they open the site.

1. InviteA team admin or club admin invites an email on the Members page, or a club admin imports a workbook. Club admins invite other club admins on the club page.INVITE#email / TEAM#t or CLUB#c, 60-day TTL
2. Sign upThe person enters that email and a password. The pre-sign-up trigger refuses emails with no invite, unless the email is a configured site owner.Cognito user, unconfirmed
3. VerifyCognito emails a 6-digit code ("Your A5 Team Hub code"); the person enters it.—
4. LinkThe post-confirmation trigger turns every invite for that email into a team membership or club-admin record, and deletes the invites.MEMBER#sub, ADMIN#sub, GSI1 USER#sub

Updated

Pushes say what changed, never the data itself. The browser then re-reads through the API, so someone who can't see the ledger never receives ledger numbers over the socket. If the re-read is refused, the page tells the person they've lost access and returns them to their teams.

11

Clubs & team lifecycle

New

Clubs and colors

A site owner adds a club and names its first admin. The club admin sets its name, short name, two colors, the links and notes every team sees on Team Info, and who else runs it. The site derives the full palette from the two colors, darkening or lightening only as far as text needs to stay readable, and previews it on the whole page while choosing. Families see their club's colors on their team's pages.

Archive, restore, delete

Archive when a season ends: the team stays, nothing can change, and families find it under Archived teams. Restore undoes it. Delete removes the team partition, its directory entry and waiting invites after the site owner types the team id. People's accounts stay. Only point-in-time recovery (35 days) can undo a delete, so R31 asks for a delayed purge.

ActionWhoReversibleEffect
Create teamClub adminDeleteClaims the id across all clubs; settings, handbook, directory entry

Hardening

New

Three waves. Wave 1 covers everything that could expose children's data or lock families out once real families sign in, so it comes before the pilot. Each recommendation names the risks it closes and where the change goes.

Wave 1 · before families use the live site

Phase 6
R1

Separate prod from dev deploys

Best: a second AWS account for prod under AWS Organizations, with its own OIDC role. Short of that, one execution role per environment, limited to that environment's stack, table and functions, and a permissions boundary required on every role it creates. Limit the dev GitHub environment to main.
